# Standard-level proposal (human review only)

Status: **proposal only**. No rule is approved by this file. The real rule files must remain `status: draft`; `level_proposed` is not an executable schema field.

Source: the repository's `standards/disa-cisco-ios-switch/Y26M04/catalog.json` (118 controls from the bundled DISA Cisco IOS Switch L2S, NDM, and RTR XCCDF files). The candidate selection below follows each control's catalog check text; applicability to a particular Catalyst 2960-X software release still requires human review.

Capability flags mean:
- `can_pass=true`: this predicate can establish the limited Standard presence claim.
- `can_fail=true`: this predicate can establish a failure for the stated check.
- `false / true`: failure detection only; a positive presence result must be downgraded to `MANUAL`.
- A Standard PASS is only a presence claim, never proof of effectiveness.

## Separate Pro candidates (applied-depth proposals)

## Human decisions needed before implementation

1. Select which proposed candidates truly define the minimum security baseline for the target Catalyst 2960-X/XR/L fleet.
2. Confirm organizational choices that the STIG leaves organization-defined (e.g. log buffer size, unused VLAN, management networks, permitted discovery protocols).
3. Confirm the target IOS/IOS XE versions and feature support for each control.
4. Review every proposed check's `can_pass`/`can_fail` behavior and false-positive/false-negative risks.
5. Keep all rule files in `status: draft`; do not add executable `level` until a human approves the design.
